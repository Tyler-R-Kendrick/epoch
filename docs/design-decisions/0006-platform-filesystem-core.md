# ADR-0006: Add Filesystem-Backed Epoch.Platform Core

## Status

Accepted.

## Context

Epoch.Platform needs production-facing behavior that survives process restarts,
can be verified before trust, and can be restored into a fresh data directory.
The in-memory Core remains useful for tests and embedded examples, but it is
not enough for operators evaluating headless platform management, backup
validation, webhook safety, or disaster-recovery flows.

## Decision

Add `createFileSystemPlatformCore()` to `@epoch/platform-core`. The filesystem
mode writes `platform-state.json` as a state envelope containing a stable
SHA-256 manifest hash and a Core snapshot. Startup verifies the hash before
restoring state and raises `state_verification_failed` when the state file has
been tampered with.

Backup runs created by filesystem-backed Core write manifest-hashed backup
artifacts under the instance data directory. Backup verification re-reads the
artifact and checks that its manifest hash matches the contained snapshot.
Fresh filesystem Core instances can restore from a verified backup artifact.
Webhook verification uses HMAC signatures generated by `signWebhookPayload()`.

## Consequences

- Core now has a durable local control-plane mode without moving business rules
  into SDK or Web.
- State files and backup artifacts are deterministic enough to hash and verify.
- Plaintext secret values remain outside persisted state and backup snapshots.
- This does not choose a production database, queue, search engine, runner
  runtime, infrastructure adapter, or clustered scheduler.

## Revisit Criteria

Revisit this decision when Epoch.Platform introduces a database-backed store,
distributed locking, online migrations, encrypted secret material storage,
remote object storage for backups, or clustered Core services.
