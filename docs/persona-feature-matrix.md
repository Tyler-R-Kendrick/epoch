# Persona Feature Matrix

This matrix applies the Community human-centered design method across the full
executable feature surface. It is the audit bridge between `features/*.feature`,
the feature registry, the [executable feature scenario inventory](feature-scenario-inventory.md),
and persona-aware BDD scenarios.

Personas are not features. They describe users whose needs shape real product
scenarios. Keep persona coverage as tags and scenario context inside product
feature files; do not create persona-only, human-centered-design-only, or
e2e-journey feature specs.

Use it when adding or changing a feature spec:

- every executable feature spec must appear here and in
  [features.md](features.md);
- every row must name the primary persona, contributor journey, pain point,
  trust question, degraded-state behavior, human considerations, and validation
  evidence;
- Community-facing rows use the default persona, **A GitHub open-source
  contributor**, unless a more specific documented persona is more accurate;
  and
- operator, maintainer, and security/compliance personas are supporting
  personas used when a feature is primarily about hosting, governance,
  moderation, or incident response that protects the contributor experience.

## Personas

Personas are **critical reviewers**, not cheerleaders. For any Community-facing
UI, they must run the [adversarial design critique](community-human-centered-design.md#adversarial-design-critique-protocol)
and treat craft, playfulness, wonder, and DESIGN.md adherence as pass/fail.

| Persona | Role in the solution | Human needs to design for | Adversarial design fails (reject) |
|---|---|---|---|
| A GitHub open-source contributor | The primary Community persona and the reference user for repository, CLI, browser, sync, review, portability, and contribution workflows. | Trustworthy current state, low-cost contribution paths, portable local work, clear security signals, accessible interrupted-session workflows, respectful async collaboration, and a product they are **proud to open**. | Lifeless wireframe; AI-slop; no place identity; worse than GitHub/Discord orientation; no craft delight or proof wonder; DESIGN.md named-rule violations. |
| A citizen builder | A person building in the open without deep version-control skills who contributes ideas, writing, design, translations, testing, and sometimes code. | Approachable contribution paths that do not require git fluency, equal credit for non-code work, plain-language trust signals, and confidence that experiments cannot break the real project. |
| A community member | A person who follows projects and people, asks and answers questions, votes, attends events, and celebrates releases without necessarily contributing changes. | One central place for community life instead of scattered chat and social apps, followable work-in-progress, welcoming discussion norms, and visible community milestones. |
| A maintainer | A contributor with project stewardship, review, moderation, release, and community-health responsibilities, including hosting the project's community and supervising agent participants that contribute concurrently. | Review clarity, abuse control, moderation transparency, contributor quality, project-health signaling, manageable contribution volume from humans and agents, and burnout reduction. | Gray mush that adds moderation load; social hangout dead; signed intent path hidden; density without hierarchy; trust meta illegible. |
| A platform operator | A person running Epoch Platform or deploying Community for a team, organization, or public forge. | Production readiness, auditability, cost visibility, rollback, degraded-state diagnosis, accessibility, and safe automation. | Would not demo without apology; inconsistent tokens; broken focus; snapshot honesty missing; “works in staging” aesthetics. |
| A security and compliance responder | A person accountable for secrets, identity, policy, audit, tenant data, signing evidence, and incident response. | Least privilege, secret redaction, safe diagnostics, retention, export/delete guarantees, and provenance. | Trust theater (decorative sigs); no live/snapshot honesty; provenance buried; playful chrome that obscures policy truth. |

## Persona Scenario Guardrail

`test/unit/persona-feature-model.test.ts` reads the `features/` directory at
runtime. It fails when a feature file treats personas as product features, when
mechanical matrix-only persona scenarios are added, when documented persona
tags are not used by real product scenarios, or when an executable feature spec
is missing from [features.md](features.md), the
[executable feature scenario inventory](feature-scenario-inventory.md), and
this matrix.

When a feature is mostly internal, document the closest human-facing reason it
exists. For example, a storage, sync, or signing feature still serves the
contributor's trust, recovery, or portability needs. If no persona can be named,
the feature needs a design note before implementation continues.
